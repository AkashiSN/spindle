# D-106 ログはファイルのまま残し、画面は API で読む。GC・スキャン・バックアップの結果はジョブの note に残す

**背景**（2026-10-15）: 操作タブが照合の詳細を `data/verify/` の実ファイルで案内していた。コンテナの中のパスはユーザが開けない。
設定画面の退避ファイルの一覧は本番で 7,570 件あり、すべて GC で実体を消した記録だった。GC・スキャン・バックアップは
結果を tracing にしか出さず、画面では「完了」しか分からなかった。

**決定**:

1. ログはファイルのまま（照合は `data/verify/<album_id>.log` に album ごとに最新 1 回分、吸い出しは album と一緒に動く
   `rip.log` / `rip<N>.log`）。画面は `GET /api/logs` で実行ごとの一覧を、`GET /api/logs/{key}/text` で本文を読む。
   本文は root の dirfd から `openat2` で開き、上限 1 MiB。照合ログの過去分は残さない（古い実行は「上書きされた」と出す）
2. 吸い出しログの場所は DB の `log_path` を使わず、その disc の active な曲がいまあるディレクトリから引く
   （`log_path` は配置時の Library 相対でリネームに追随しない。名前だけ使い、`rip*.log` 以外は読まない）
3. GC・スキャン・バックアップの結果は `Outcome::DoneWith` でジョブの `note` に残す（1 行目を一覧に、全文を展開に）。
   ジョブ行の保持期間（done 7 日）で一緒に消える。別の表は作らない
4. 編集履歴と退避ファイルとログを ☰ の「記録」画面のタブにまとめる。退避ファイルは保持中を既定にして 100 件ずつ

**理由**: ログを DB に入れると照合のたびに数十 KB の行が積もり、ファイルが正という原則（不変条件 1）とも二重になる。
読む経路だけ足せば、既存の書き手（照合・吸い出し・配置）は変えずに済む。結果の要約は数行なので、ジョブ行に
載せればジョブ画面からそのまま見えて、保持の規則も既存のものに乗る。

**追記**（2026-10-20、設計書の吸収）: 作らなかったもの — サーバのアプリログ（tracing）を画面に出すこと、バックアップの
世代一覧、`scan_runs` の一覧画面、照合ログの過去分の保存。`GET /api/archive` は呼ぶのが記録画面だけなので、互換を
保たずに形を変えた（`items` / `next_cursor` / `counts`）。ログ一覧の `key` と `cursor` は不透明な文字列にし、画面は中身を
読まない（本文の取得と続きの要求に渡すだけ）。照合ログの本文は DB の `log_path`（絶対パス）を使わず、`data/verify` の
dirfd から `<album_id>.log` の名前を組み立てて開く（DB の値をパスとして信じない）。rip のジョブ行に「ログを見る」を
出さないのは、rip ジョブは Inbox に置くまでで album を知らないため（承認前の吸い出しログは Inbox の件から
`GET /api/inbox/:id/files/:name` で読む）。ジョブ画面のエラーは `title` のツールチップをやめて行の展開に出す
（ツールチップは選択・コピーができず、タッチ端末では出ない）。設定画面の category の使用数は削除の可否の判定と
同じ関数で数え、押してから 409 で断られる前に理由を見せる。
