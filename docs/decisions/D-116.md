# D-116 購入音源はブラウザからアップロードし、分け方を確かめてから Inbox に置く。状態はステージングのマニフェストが正

**背景**（2026-11-25）: ダウンロード購入した音源（mora などのハイレゾ FLAC。MP3 / AAC しか売っていないものもある）を入れる
手段が無かった。入口は CD（吸い出し）と YouTube（ytdl）だけで、[§5](../spec/05-library-layout.md) は「Inbox/（ハイレゾ購入分などを
ここへ置く）」と書くが、置く手段が無い。ユーザから聞いた使われ方: 届く形は zip のことも、ファイルそのままのこともある。1 回は
基本アルバム 1 枚分だが、ハイレゾはシングル 1 曲単位で買うので、ばらばらのシングル数枚をまとめて入れることも多い。操作は PC の
ブラウザだけ。外（Cloudflare Tunnel 経由。無料プランは 1 リクエスト 100 MB まで）からも数 GB のアルバムを送りたい。

**決定**（仕様は [§7.12](../spec/07-pipeline/12-upload.md)）:

1. **入口はナビのタブ**（`ライブラリ / アルバム / CD / YouTube / アップロード / Inbox / 端末`）。CD・YouTube と並ぶ入力の 1 つで、
   右隣の Inbox に数字が増える今の導線（[§12.1](../spec/12-ui/01-skeleton.md)）に乗る。スマホ版には出さない（取り込みは PC。
   [D-115](D-115.md)）。画面は番号付きの段（① ファイルを選ぶ → ② 送信 → ③ Inbox での分け方 → ④ Inbox へ置く → ⑤ Inbox で承認）。
   モックで合意した
2. **送ってから分け方を確かめて Inbox に置く**。選んだ時点で送り始め（確認を挟まない）、サーバがタグで件（アルバムアーティスト +
   アルバム）に分けて状態（ライブラリに同じ音声がある / Inbox に同じ件がある / 既存の album に追記 / 名前が無い / 新規）を返し、
   人がまとめる・外すを済ませてから置く。Inbox に置いた後の承認・配置・後続は既存のまま（[§7.8](../spec/07-pipeline/08-inbox.md)）
3. **状態の正はステージングのマニフェスト** `Inbox/.spindle-upload-<id>/upload.json`。DB に表を作らない。置き場所を
   Inbox 直下の隠しディレクトリにするので、走査に拾われず、公開が同じデータセット内の rename で済む
4. **マニフェストはアップロードごとのプロセス内の鍵で直列にする**（`UploadLocks`。main が 1 つ作り API・upload ジョブ・GC が共有）
5. **送信は 32 MiB のチャンク**、同時 2 ファイル。`.part` の実際の大きさが正で、マニフェストの `received` は写し。ファイル途中からの
   再開はしない（途中のファイルは最初から送り直す）。予算はアップロード全体で、宣言サイズ + 展開した量 + GC 待ちで数える
6. **zip 本体は公開か破棄まで残し、展開は世代ごとに新しいディレクトリへ書く**。成功したら世代を切り替え、古い・失敗した世代は
   `garbage` に載せて GC に消させる。危ないエントリ（パス規則違反・symlink・大小文字だけ違う同名など）はそのエントリだけ拒否して
   続け、壊れた・暗号化された・上限を超える zip は全体を失敗にする
7. **公開は凍結した計画で段階的に行う**。「Inbox へ置く」でその時点の分け方を計画としてマニフェストに凍結し、件ごとに
   組み立て（`publish/<n>/` へ移す）→ 宛先をマニフェストに書く → rename、の段階を進める。凍結の後は ③ の変更も「捨てる」も
   受け付けない。全件を置いたら、公開より後に走る Inbox の走査を確保できたときだけ終わりを記録する
8. **件のディレクトリは平らにする**。サブフォルダ（`Disc 1/` `Booklet/` など）は件の直下へ集め、名前がぶつかれば親フォルダ名を
   前に付ける（`Disc 2 - 01 Track.flac`）。それでもぶつかれば ` (2)`
9. **同梱ファイルに PDF と画像を足し、アップロード以外の件にも同じ規則を当てる**（`is_companion_name` に `pdf` `jpg` `jpeg` `png`
   `webp`）。同梱ファイルの付け先は、曲と同じディレクトリの件 → 全曲が同梱ファイルのディレクトリの下にある唯一の件 → 件が
   1 つだけならその件 → どれにも付けない、の順
10. **「Inbox に同じ件がある」は置き場所の名前だけで判定する**。Inbox の他の件との音声の一致は見ない。置き場所が既にあれば
    ` (2)` の別のディレクトリにし、既存の件に混ぜない
11. **放置したものは GC が片付ける**。公開も破棄もされず `[upload].stale_days`（既定 30）経ったものを破棄扱いにし、捨てたもの・
    公開後の残り・古い展開世代は `[gc].retention_days` 後に GC（区分 G）が消す。消す直前に鍵を取って読み直す（[D-90](D-090.md) と同じ）

**理由**:

- 1: 購入音源は CD・YouTube と同じ「入力」で、行き先も同じ Inbox。独立した画面にすると右隣の Inbox を見る今の導線がそのまま効く。
  スマホから数 GB を送る用途は無く、確認も PC で行う
- 2: ばらのシングルをまとめて送ると件がいくつもでき、ライブラリに既にある曲が混ざることもある。Inbox に置いてから 1 件ずつ却下・
  削除するより、置く前に一覧で外す・まとめる方が早い。置いた後を作り直さないので、承認画面には出どころと同梱ファイルの表示を
  足すだけで済む
- 3: 不変条件 1（ファイルが正、DB はキャッシュ）。アップロードの状態はステージングの実体と切り離せず、DB に写すと二重の正になる。
  マニフェストと実体だけで一覧・再開・照合ができれば、DB を消しても失わない。ジョブ行が消えても照合（起動時と一覧の取得時）が
  投入し直す
- 4: 同時 2 本の送信・PATCH・展開・公開・GC が同じマニフェストを読み書きするので、直列にしないと更新を失う。鍵はプロセス内の
  ステージングに対するもので、SMB の他プレイヤーと共有するライブラリのファイルの排他ロック（不変条件 5 の禁止）ではない
- 5: Cloudflare Tunnel の 1 リクエスト 100 MB の上限の内側に収める。サーバの本文の上限はチャンク + 余裕の 40 MiB。中身を
  覚えていないブラウザで途中から再開するより、ファイル単位の送り直しが単純。予算をアップロード全体で数えるのは、zip を展開すると
  同じ内容が 2 倍のディスクを使い、外した・壊れた実体も GC まで残るから
- 6: 展開先を「先に消してから書き直す」と、物理削除を GC 以外が行うことになり（禁止事項）、途中で落ちたときに成功した世代まで
  失う。世代を分ければ再実行は新しい世代へ最初から書くだけで冪等になる。zip 本体を残すのは、展開をやり直せるようにするため
  （ディスクは一時的に 2 倍使う）。危ないエントリ 1 つで全体を止めると、購入した zip に紛れた `__MACOSX` や symlink のせいで何も
  入らなくなる
- 7: 公開は複数の件の rename で、途中で落ちうる。計画を凍結しておけば、再実行は計画と実体だけで続きから進められ、その間に ③ が
  変わって置くものがずれることもない。宛先を書いてから rename するので、rename の後に落ちても宛先が分かる。走査を確保してから
  終わりを記録するのは、実行中の走査が新しい件を見ずに終わると、置いた件が次の変化まで Inbox に出ないため
- 8: Inbox の走査は「音声のあるディレクトリ 1 つ = 1 件」で、配置が持っていく同梱ファイルも件の直下だけ。サブフォルダのまま置くと
  複数枚組が別の件に分かれ、ブックレットは Library へ行かない。音声の Inbox 上の名前は配置でテンプレートの名前に変わるので、
  別名にしても後に残らない
- 9: 購入音源にはブックレット PDF や追加の画像が付き、それをライブラリのアルバムのフォルダへ一緒に持っていくのがゴールの 1 つ。
  `is_companion_name` は配置・却下した件の削除・一括リネームの追随で共有しているので、同じ規則にしておかないと、配置で移した
  PDF が却下した件の削除やリネームで取り残される。`Album/cover.jpg` の下に `Disc 1/` `Disc 2/` がある形はよくあり、同じ
  アップロードに別の件があるだけで付け先が決まらなくなるのを避けるため、全曲がその下にある唯一の件に付ける
- 10: `inbox_files` には音声の指紋が無く、Inbox の他の件と照らすには実体を開いて計算し直すことになり重い。置き場所の名前が
  同じなら同じアルバムの可能性が高く、知らせるには足りる。既存の件に混ぜると、人が見ていないファイルが承認済みの件に入る
- 11: 送ったまま放置したものが際限なく溜まらないようにする。物理削除は GC だけ（禁止事項）

**却下**:

- 確かめずにそのまま Inbox に置く（ばらのシングルや重複を Inbox で 1 件ずつ却下・削除することになる）
- アップロードの状態を DB の表に持つ（二重の正。DB を消すと再開できなくなる）
- 1 リクエストでファイルを送る（Cloudflare Tunnel の 100 MB 上限）。ファイル途中からの再開（ブラウザが中身を覚えていない）
- サブフォルダのまま置く（走査で別の件に分かれ、同梱ファイルが Library へ行かない）
- Inbox の他の件と音声で重複を判定する（重い）。同じ置き場所の既存の件へ足す（見ていないファイルが混ざる）
- ストアの API 連携・自動ダウンロード、スマホからのアップロード、Inbox の件同士を後からまとめる操作（範囲外）

**追記**（2026-11-25、実装で決めたこと。設計書になかった・設計書と違うもの）:

- **公開の止まった失敗を残す**（`publish_error`）: やり直しても変わらない公開の失敗（置き場所の途中が通常ファイルの ENOTDIR を
  含む）と、最後の試行の失敗はマニフェストに残し、照合は投入し直さない（画面は動いている間 2 秒ごとに一覧を取り直し、そのたびに
  照合が走るので、残さないと失敗するジョブが 2 秒ごとにできる。最後の試行で残さないと、ジョブは `failed` で照合も投入せず、
  捨てることもできない行き止まりになる）。押し直しが消して投入し直す。`publish_error` があって upload ジョブが動いていなければ
  `DELETE` で捨てられる（押し直すしかないと永久に残る）。捨てた後の押し直しは、計画を置き終えていなければ 409 `busy`。止まった
  ものは放置の対象にしない
- **GC が消す壊れたステージングを絞る**: マニフェストが無いか JSON として壊れているものだけを消す（捨てる印も付けられる）。
  読み取りの I/O の失敗（EIO・EACCES）・新しい版・id の食い違いは一覧に `deletable: false` で出すだけで、捨てられず GC も
  消さない。一時的な障害や、戻した後の古い spindle から見た新しい版のマニフェストを消すと取り返せないため
- **読み取りの覚え**（`StagedReadCache`。メモリだけ）: 2 秒ごとの取り直しで数 GB の指紋を計算し直さないよう、ファイルの
  `(inode, size, mtime)` が同じならタグと指紋を読み直さない
- **壊れた origin は凍結を止めない**: 外したものと同じ扱いで計画から外す（止めると人が外すまで置けない）。③ には「壊れた」と出る
- **入れる件が 0 の公開は 409 `empty`**（設計書は 400）。画面はコードだけを見る
- **一覧は 1 つの失敗で落とさない**: 表示を作れないアップロードは `broken` に理由を付けて出す
- **選択の写し** `choices`: `PATCH` は項目を丸ごと置き換えるので、表示が今の `merges` / `excluded_*` / `included_*` を返し、画面は
  前の応答を反映してから次の `PATCH` を作る（変更を直列にする）
- **展開に失敗したジョブは `done`**: 失敗はマニフェストの `zip.error` にあり、やり直しは API（「展開し直す」）から行うので、ジョブは
  note に理由を残して終える（ジョブ画面では失敗に見えない）。取り消しは `cancelled`
- **最後のチャンクの後に落ちたもの**: `.part` が `total` に達したままなら、次の要求でサーバが正式な名前へ進めて完了にする
  （クライアントに頼らない）。`offset == total` の空の PUT は完了の確かめとして受ける
- **展開の予約は予算の残りまで**: 次のブロック 8 MiB を予約するが、予算の残りが少なければその残りまで（そうしないと上限の手前で
  断ってしまう）。予約は書く前のまま
- **置き場所の名前を隠し名・長すぎる名前にしない**: 各要素は `.` で始まれば `_` を前に付け、200 バイト以下に切る（走査が飛ばす
  件を作らない）
- **取り込まないファイルも受けて保存する**: ③ に出すため（画面は隠しファイルをはじめから送らない）。外した origin は戻さない
  （同じパスを送り直すと別の origin になる）
- **同梱ファイルの付け先**: 同じディレクトリの件が複数あれば表の先頭の件。設計書の「件が 1 つならその件」に「全曲が同梱ファイルの
  ディレクトリの下にある唯一の件」を足した（上の 9。祖先は要素単位で比べ、`Album` は `Album 2` の祖先にしない）。件が 1 つだけの
  ときは、曲のフォルダの隣の `Booklet/` のように祖先でなくてもその件に付ける（前からの振る舞い）。どの件にも付かないものの
  付け先を選ぶ UI は作らない
- **平らにした名前は 255 バイトまで**: 親フォルダ名を前に付けた名前や ` (n)` を付けた名前が上限を超えるなら、親フォルダ名か拡張子の
  前を文字境界で切る
- **件を入れ直しても、既定で外れた曲（ライブラリに同じ音声がある曲）は入らない**: 曲は個別に入れ直す
- テストのためだけに、Inbox の走査が歩き終えた後に呼ぶ口（`InboxHandler::with_after_scan`）を足した（本番では設定しない）。
  走査と公開が重なる場合を再現する手段がほかに無いため
