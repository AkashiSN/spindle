## D-109 Android の同期の進捗は job イベントの detail で流し、Mac と同じ表示を使う

**背景**（2026-10-16）: D-108 で Mac の同期には進捗が付いたが、Android（adb）の `device_sync` は件数の進捗を SSE で流していたが、
端末タブは使わず「同期中…」としか出さなかった。数百 MB 以上を送る間、どこまで進んだか、速度、残り時間が分からなかった。

**決定**:

1. 進捗は `device_sync` ジョブの `job` イベント（SSE）の detail に載せる。形は
   `{"kind":"device_sync","phase","current","bytes_done","bytes_total","rate"}`。件数は `JobEvent` の `done` / `total`
   をそのまま使う。D-108 の `device_progress`（Mac のエージェントが送る進捗）は使わない。detail は SSE にだけ流し、
   DB の進捗の書き込みは既存の `JobContext` の間引き（250 ms）に任せる
2. 段（`phase`）は `delete` / `move`（パス変更のバッチ）/ `send`（更新・追加）/ `playlist`。Mac の `fetch`（受信中）は
   使わず、画面の見出しは `send` を「送信中」とする。`current` は送り先（削除は `from`）のファイル名、プレイリストは
   そのファイル名
3. `bytes_total` は端末へ中身を送る曲（`Add` / `Update` / `UpdateMove`）の `size` の和。引き継ぎの照合で済む曲
   （`adopted_unchanged`）は送らないので含めず、純粋な `Move` も含めない。`bytes_done` は**曲を 1 曲処理し終えるごと**に
   増やす（曲の途中では増えない）。保留（開けない・衝突・照合失敗など）になった曲の `size` も処理し終えた量として足し、
   バーを最後まで進める。パス変更のバッチは失敗した曲を外してやり直すことがあるので、バッチの中では送り終えた量の
   最大値を見せて減らさず、バッチを終えたら（成功・中断のどちらでも）バッチの全体を確定させる
4. エンジンは各項目の始め（`current` を入れて）と終わりの両方で `progress` を呼ぶ。パス変更のバッチは、仕上げ
   （空ける・置く）でもメンバーごとに `current`（送り先のファイル名）を出し、置くたびに件数を 1 進める（純粋な `Move` は
   準備の段で何もしないので、ここで出さないと今の曲が空のまま、または更新 + 移動の曲名が残る）。バッチを終えたら件数を
   「バッチの開始時の件数 + バッチの項目数」に確定させる（置いた分を二重に足さない。外した曲もここで数える）。通知は
   失敗せず、耐久化と `mv` の順序は変えない。速度（`rate`）は `JobControl` が
   `(時刻, bytes_done)` の標本を直近 5 秒だけ持ち、D-108 と同じく 5 秒前以前で最新の標本を基準（無ければ 0）に
   バイト差 ÷ 経過秒で出す。標本が 1 つ・経過 0 なら 0。純粋関数にして単体テストする
5. 画面（端末タブ）は、`sync_job` の job の進捗を受けているとき（一覧の state が queued のままでも。running の間だけ表に項目がある）に D-108 と同じ進捗の行
   （`SyncProgressLine`）を出す。無ければ従来どおり「同期中…」。**「応答なし」（30 秒）は Android では出さない**
   （ジョブの生死はワーカーが管理し、パス変更のバッチのように間が空く段がある）。ページを開き直したときは、
   次の `job` イベントが届くまで「同期中…」のまま（DB の件数を一覧に足さない）

**理由**: ジョブにはもう進捗の仕組み（`JobEvent` と SSE）があり、新しい API や保持場所を作らずに済む。進捗は表示の
ための一時的な値で、DB に書く必要が無い（D-108 と同じ）。バイトを曲の完了ごとに数えるのは、1 曲の転送の途中を
ストリームから測るとエンジンの構造（照合と `mv` を含む曲の単位）に手を入れることになり、曲が数 MB〜数十 MB の
この用途では粗さが気にならないため。保留の曲の `size` を足すのは、足さないとバーが合計に届かずに終わるため。
「応答なし」を出さないのは、生死の判定をジョブの回収（D-76）が持っており、画面が二重に判定すると、間の空く段で
誤って警告するため。
