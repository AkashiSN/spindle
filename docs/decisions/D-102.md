# D-102 印のついたプレイリストの削除は印の変更と同じ規則にし、終端した計画は GC が回収する。DB 全損後の引き継ぎと id の再利用は後回しにする

**背景**（2026-10-09。P5-6）: P5-5 で [SPEC §17](../spec/17-open-issues.md) に残した端末配信の 3 件（プレイリスト削除と `generation`、終端した計画の回収、DB を失ったときの保存先の引き継ぎ）を調べた。

1. **プレイリストの削除**: 素の `DELETE` で、印だけが CASCADE で消える。`generation` は進まず、open な計画も止めない。調べると、`runnable` と報告の検証が吸収するので間違った結果や詰まりにはならない。ただし実行中の同期が、消えたプレイリストとその曲をいったん端末に書く無駄が残り、`generation` の定義（印を変えるたびに進める）とも合わない
2. **終端した計画**: `device_sync_plans` の終端の行を読むのは `finish` の再送判定だけで、消えるのは端末の削除だけ。1 回の計画は初回の全曲で 3〜4 MB、最悪で数十 MB あり、初回の大きい計画の破棄と取り直しを繰り返すと DB とバックアップが太る
3. **DB 全損後の引き継ぎ**: 設計書は manifest の `device_uuid` を新しい行に写すだけとしていたが、DB を作り直すと `tracks.id` / `playlists.id` が振り直される。端末の正本（manifest、Mac のエージェントの state）は id をキーにするので、uuid だけ写すと manifest の `track_id` が新しい DB の別の曲を指し、差分は他人のファイルを移動して上書きする。Mac では `Update` / `UpdateMove` がミュージック.app の track を保ったまま location を付け替える（[D-101](D-101.md)）ので、再生回数・レート・追加日が別の曲に移る

**決定**:

1. **プレイリストの削除は印の変更と同じ規則**: 印のついた端末のどれかに open な作業（open な計画か待ち・実行中の `device_sync`。`has_open_work`）があれば 409 `open_plan`（端末名を message に出す）。通れば、印のある端末の `generation` と `updated_at` を進め、プレイリストを削除する。確認から削除までを 1 つの SAVEPOINT で行う。印の無いプレイリストの削除は今までどおり。プレイリストの中身・名前・ルールの変更は止めない
2. **終端した計画は GC が回収する**: `completed` / `abandoned` で `closed_at` が `[gc].retention_days` より古いものを消す。端末ごとに最後の終端 1 件は残す（長く寝ていた Mac の報告の再送を 200 で受ける保険）。open は対象外（`close_plan` は `WHERE state='open'` の CAS なので競合しない）。`GET /api/gc/preview` に `plans`（消す件数）を足す。マイグレーションと設定は足さない
3. **DB 全損後の保存先の引き継ぎ（P5-7 Android、P5-8 Mac）と id の再利用は作らず、TASKS に残す**。引き継ぎは uuid を写すだけでは誤りで、`canonical_key(dest_path)` による id の付け替え（トークンは端末の sha256 が今の送る元と一致すれば今の配信トークン、違えば STALE）が要る。`dest_path` は Library の `rel_path` の拡張子だけを替えたもので、DB を作り直しても同じになるため。Android と Mac を別の PR にする。Mac が本命（再生回数の保全）だが、Android の方が閉じていて試しやすいので先に作る
4. **SPEC の §17 は、この 2 件は [x] に変えて残し、引き継ぎ（id の付け替えが要ることを書く）と id の再利用（`AUTOINCREMENT` でないので GC が最大 id の行を消すと再利用される。Mac で再生回数が別の曲に移りうる）を残す**

**理由**: 削除を印の変更と同じ規則にすると、`generation` を進めるのが open な作業が無いと確かめたのと同じトランザクションの中だけになり、説明がつく。終端した計画は読む箇所が少なく、消えて困るのは遅れた再送が 404 になることだけで、エージェントは次の sync で自動回復する。引き継ぎは id の付け替えを伴い、設計書より大きい（600〜1,000 行、Android と Mac で別 PR）ので、今回の小さな 2 件と混ぜない。

**却下**:
- 削除で `generation` だけ進める（止めない）: open な agent の計画がある間に進めると、エージェントの報告も破棄も 409 `generation_mismatch` になって閉じられず（UI の強制破棄だけが逃げ道）、adb の実行中の同期は `GenerationChanged` で失敗する。PUT が「進める」と「open な間は 409」を組にしているのはこのため
- 今の挙動を仕様にする（削除は止めず `generation` も進めない）: 正しさは保たれるが、実行中の同期が消えたプレイリストを一度端末に書く無駄が残る
- 閉じるときに同じ端末の古い終端を消す（保持期間なし）: 履歴が残らず、設計書・SPEC の「GC が保持期間後に消す」と変わる
- uuid を新しい行に写すだけの引き継ぎ（設計書どおり）: 上の背景 3 のとおり、全曲が誤った更新・移動になり、Mac では再生回数が別の曲に移る。今の「片付けて登録し直す」より悪い
- 登録で管理外の同一ファイルを内容で引き取る: 「管理外のファイルには触らない」に例外を作り、sha256 の全曲計算が要り、Mac では persistent ID を引き取れない
