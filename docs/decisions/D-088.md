# D-88 マイグレーションを最初のリリースの前に 1 回だけ `0001_init.sql` へ畳む

**決定**（2026-09-24。ユーザ依頼。[D-79](D-079.md) / TASKS P4-12 (8) の方針どおり）:

- `db/migrations/0001`〜`0024` を、最終形のスキーマを直接作る `0001_init.sql` 1 本に置き換える。列の並び・
  CHECK・既定値・索引・トリガ・ビュー・種データ（`export_profiles` の 3 行）は 24 本を流した結果と同じ
  （空 DB へ流した `sqlite_master` をコメントと空白を除いて比べ、全表の `table_xinfo` / `index_list` /
  `index_xinfo` / `foreign_key_list` と行を比べて一致を確かめた。違うのは `sqlite_sequence` に
  `playlist_subscriptions` の行（seq 0）が無いことだけで、次の id が 1 なのは同じ）
- 0006 の Rust 側の手当て（既存プレイリスト名の衝突の改名と `idx_playlists_name_key` の作成。`post_sql`）は
  消し、索引は SQL に直接書く。`foreign_keys=OFF` で流す版の一覧（`FOREIGN_KEYS_OFF`）は空にして仕組みは
  残す（以後 CHECK を広げるために表を作り直す版で使う）。各版のアップグレード試験は、それが守っていた
  最終スキーマの性質を空 DB に対する試験へ移した（`tests/migrations.rs`）
- 版 24 までの既存 DB を新しいバイナリで開くと `Newer`（DB の版 24 > バイナリの最新 1）で起動しない。
  `edge` は DB の互換を約束しない（[D-79](D-079.md)）ので許容し、リハーサル環境はリリース時の再移行で DB ごと作り直す
  （MIGRATION §5）。以後は CLAUDE.md の禁止事項どおり、既存ファイルは書き換えず連番を足す

**理由**: 公開イメージを誰かが pull して DB を作った後は既存ファイルを書き換えられないので、畳めるのは
最初の `vX.Y.Z` より前、DB を作り直すこの時だけ。24 本のうち 8 本は表の作り直し（CHECK を ALTER できない
ため）で、新しい DB を作るたびに同じ表を何度も作っては捨てていた。スキーマの正を 1 ファイルで読めるように
する。

**却下**: 畳まずに残す（空 DB の構築が作り直しの連鎖のままで、スキーマの全体を読むのに 24 本を追う必要がある）。
版 24 の既存 DB を新しい 0001 の版 1 へ読み替える手当てを入れる（互換を約束しない `edge` のためだけの
コードが残り続ける。リハーサル環境は作り直す）。

**追記（2026-09-26。ユーザ依頼）**: 「1 回だけ」を「最初の `vX.Y.Z` より前に限る」と読み替え、リリース直前に
もう一度畳む。D-88 の後に 0002〜0004 が増えた（Inbox の破棄・表の画像・category の索引）。理由は本文と同じで、
畳めるのはリハーサル環境の DB を捨てて作り直す最初のリリースの時だけ。タグを切った後は既存ファイルを書き換えない
（TASKS P4-12 (10)、MIGRATION §5 の手順 0）。2026-09-26 に畳んだ。3 本とも列・索引の追加だけで、空 DB の最終スキーマは
`ALTER TABLE ADD COLUMN` が `sqlite_master` の SQL に残す空白の位置を除いて一致。既存の DB（版 4）は新しいバイナリ
（最新 1）で `Newer` になり起動しない（本文と同じく許容。リハーサル環境は §5 の手順 1 で作り直す）。
