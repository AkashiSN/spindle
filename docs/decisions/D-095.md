## D-95 端末への配信を管轄に入れる。Android は ADB 直結、iPhone は Mac のミュージック.app を中継し、端末ごとのマニフェストを毎回計算する

**決定**（2026-09-29。ユーザ依頼。仕様 docs/superpowers/specs/2026-09-29-device-delivery-design.md）:

- SPEC §1 の非目標「Android へは Derived + m3u8 のファイル同期を継続する」と §7.7 の「`sync.py`（ADB）は
  移植しない」を改め、端末への配信を管轄に入れる
- Android（Poweramp。SD カード or 内部共有ストレージ）は TrueNAS に USB で直結し、特権を持つ adb サイドカー
  越しに差分を送る。**差分を見てからボタンで**送る（自動では送らない）
- iPhone は純正ミュージックを使うため Mac のミュージック.app を中継する。常駐しない CLI `spindle-agent` が
  Mac 側のコマンドで反映し、iPhone へは Finder 同期
- 端末ごとに「あるべき状態」（マニフェスト）を保存せず毎回計算する（D-78 と同じ）。端末側（manifest /
  エージェントの報告）が正で、`device_items` はキャッシュ
- 曲は desired / hold / remove に分け、hold（待ち・エラー）の既存の写しには触らない。パス衝突は曲単位で保留
- トークンは意味トークン（版）と配信トークン（版 + sha256）の 2 層。送る元のハッシュは `source_hashes` に
  事前計算し、配信時に開いた FD の identity で照合する
- **不変条件の例外**: 端末上の写しと Mac の `~/Music/spindle` は Library から再生成できる複製なので、物理削除
  （`missing_since` の猶予なし）と `edit_batches` に載せない書き込みを許す。「ファイルが正」は端末側にも
  当てはめる。生 SQL の禁止は変わらない

**理由**: 端末に何が入っていて何が古いかが spindle から見えず、一括編集のたびに人が送り直しを判断していた。
android プロファイルの m3u8 は Derived と Library の 2 root にまたがり、端末へそのまま運べなかった。
Linux から純正ミュージックへ直接書き込む手段は現行 iOS に無い（メディア DB が非公開、libgpod は非対応）。

**却下**: 配信ツリーを NAS 上に実体化（Derived と同量をもう一度持つ）。spindle の外のスクリプト（状態が
見えず、2 root 問題をスクリプトで吸収することになる）。Linux から純正ミュージックへの直接書き込み（不可能）。
Apple Music のライブラリ同期（契約が要り、照合で音源が差し替わる）。常駐エージェント（ユーザが Mac 側での
起動を選んだ）。接続即同期（ユーザが差分の確認を選んだ）。パス衝突で端末全体を止める（1 件で全体が止まる）。

**実装（P5-1）**:
- `source_hash` ジョブは CPU の共通並列予算（D-73）の対象（並列度 2）。全曲分の SHA-256 は CPU も使う
- 原本のハッシュは、`source_hashes` の identity（inode・size・mtime_ns・ctime_ns。dev は見ない。D-62）が `tracks` 行と一致するときだけ有効。違えば「ハッシュ計算中」に戻して取り直す（外部ツールが同じタグで再保存した原本を「変化なし」と誤判定しないため）
- `source_hash` ジョブは原本について、開いた FD の identity が `tracks` 行と違う（または見つからない）ときは読まずに「スキャン待ち」で終える（スキャン前に読んでも差分側で使われず、差分を開くたびに全体を読み直す空回りになるため）。Derived の実ファイルが無いのは D-51 の drift なので失敗にする
- 端末の差分は、行き先を「パスを変えない管理下の曲」（保留中の曲を含む）が占めていれば、その曲をパス衝突で保留にし、不動点まで繰り返す（入れ替えの片側が保留になれば、もう片側も保留）。プレイリストはこの衝突を解いた後の desired / hold から組み立てる（保留になった曲を塞がれた行き先のパスで載せない）
- 系統が設定に無い（`derived_variants` に行が無い）端末は凍結と同じ扱いで、音声版が一致する既存の Derived と opus の非可逆原本は送る
- パス長の上限に数える root の前置きは端末から求める（adb は `/storage/<volume>/<root>/`、内部ストレージは `/storage/emulated/0/<root>/`。agent は `Music/spindle/`）
- P5-2 / P5-3 / P5-4 へ持ち越し: Derived の実ファイル欠損（D-51 の drift）を「送る元が無い」保留理由にし、`source_hash` の再投入を抑えて transcode へ誘導する / プレイリスト操作の順序（削除を先に）と改名の 2 段 / エラーのプレイリストが古い写しと衝突する場合 / agent のプレイリストの dest_path / プレイリストのパス長とトラックの `.spindle` 予約名 / `compute` を 1 つの読み取りトランザクションにする

**実装（P5-2）**（2026-09-29）:
- Inbox の段（B）の対象は、その件で配置した曲。マイグレーション 0003 で `inbox_item_tracks(item_id, track_id)` を足し、配置のトランザクションで書く（既存アルバムへの追記でも、前からある曲を数えない）。0003 以前に配置した件は曲の記録が無いので、段が対象外に見える
- Derived の実ファイル欠損（D-51 の drift）は自動で作り直す。`source_hash` が Derived を開けず NotFound なら、その曲・系統の transcode が queued / running でなく、行の `rel_path` も読んだときのままであることを同じ書き込みトランザクションの中で確かめてから `derived_files` の行を消し、`enqueue_if_stale` で作り直しを投入する。差分には「Derived 未生成」と出る
- スナップショットのキャッシュ: 全端末の差分の計算結果を `Db` が持ち、書き込みの通番（`Db::write` を通るたびに ++。読み取りの前に通番を読む）が変わるまで使い回す。通番は「読んだ時点以後の書き込みを含むかもしれないが、それ以前の書き込みは必ず含む」ので、古い結果を新しい通番で返すことは無い
- キャッシュの計算は 1 本にまとめる（ロックを持ったまま計算し、同時に外れた要求は待って同じ結果を使う）。表示だけに使う呼び出し（一覧・詳細の行の端末の状態、Inbox の段、端末一覧の件数）は、計算から 2 秒以内ならその後の書き込みがあっても使い回す（ジョブが続く間は通番がほぼ毎回進むため）。差分・plan_token・変更 API の応答・未反映の集合とスマートプレイリストの評価（書き込みの材料）は通番の一致を要する。端末が 1 台も無ければ一覧・詳細はスナップショットを取らない
- `source_hash` の投入: 差分の計算（`GET /api/devices` と差分）のたびに、未完了の dedup キーと抑制中のキーを 1 本の問い合わせで除き、残りを 1 つの SAVEPOINT で投入する。読みプールで絞って何も無ければ書き手に触らない（通番を進めない）。Web はジョブの完了による端末の取り直しを末尾の間引き（3 秒、最長 10 秒）にする
- 原本の物理同一性が `tracks` と食い違う（SMB 越しの外部の書き換えで、まだ走査していない）と、`source_hash` は走査待ちで終わる。このとき増分スキャンを投入し、note に走査待ちの印を残す。原本の payload には投入時の `tracks` の物理同一性（inode・size・mtime_ns・ctime_ns）を入れ、同じ dedup キーの最新のジョブが走査待ちで終わっていて payload の物理同一性が `tracks` の現在の値と同じ間は再投入しない（走査で `tracks` が変われば再び投入される）。抑制がないと、完了 → SSE → 一覧の取り直し → 再投入が秒に数回回り続けた
- 評価待ちの印（`ReevalFlag`）は `source_hash` と `thumbnail` の完了では立てない（端末の選曲に載るプレイリストは端末のフィールドを使えないので、端末の状態だけの変化では結果が変わらない）。再評価そのものの合図はこれまでどおり
- `device_pending` の集合は呼び出し側が渡す: DSL の `compile` は DB を知らない純粋関数のままにし、`PendingSets`（端末の `name_key` / id → 未反映の track_id 列）を引数で受け取る。SQL には `t.id IN (SELECT value FROM json_each(?))` として JSON 配列をバインドする。保存前の検証（`check`）は空の集合で行う。`Selection::Filter` の filter は `Box<Filter>` にした（PendingSets を足して enum が大きくなったため）
- `on_device` / `device_pending` の値は端末名。`canonical_key(値)` と `devices.name_key` を比べる。知らない端末名は空集合（端末の改名・削除でルールが壊れて保存できなくなるのを避ける）。演算子は `IS` だけ（それ以外は 400）。これらを使うスマートプレイリストは端末の選曲に載せられない（循環の禁止）
- 曲ごとの状態は `synced` / `pending`（追加・更新・移動・更新 + 移動）/ `waiting` / `error` / `removing`（対象外で、次の同期で端末から消える）。対象外で端末にも無い曲は状態を持たない。同期・報告で出た `device_errors` の track 行は、その曲が未反映なら理由として添え、反映済みなら `error` にする
- 容量の見積もり（差分の `estimate`）: `transfer_bytes` = 追加・更新・更新 + 移動の size の合計、`peak_bytes` = 仕様 ⑤ の実行順（削除 → パス変更のバッチ → 更新 → 追加）に沿って「今より増える量」の最大値（負なら 0）。`free` は P5-3 まで `null`。余裕（64 MiB など）は同期の実行時（P5-3）に足す
- 選曲の見積もり: `GET /api/devices/:id/estimate?selection=…&playlist_ids=…` が、仮の選曲の曲数（重複除く、missing とマルチチャンネルを除く）と、送る元のハッシュが取れている分の size の合計・取れていない曲数を返す
- PATCH で変えられるものは `name` / `selection` / `variant`。`name` 以外は generation を ++ し、open な計画・同期中は 409 `open_plan`。adb の保存先の変更は P5-3
- ナビのバッジは `GET /api/devices` の件数（追加 + 更新 + 移動 + 削除 + エラー）の全端末の合計。60 秒のポーリングとジョブの完了で取り直す（新しい SSE イベントは P5-3 で同期の進捗と一緒に足す）
- 端末へ送るの切り替えは端末ごとに PUT を直列にし、PUT の本文は実行時に「望む選曲」から作る（続けて押したときに先の変更を消さない）
- 差分表は先頭 1000 行だけ描き「ほか N 件」と出す（初回同期は 9,000 行規模）
- `JobType` の serde 名を snake_case にして `as_str` と揃えた（`playlist_sync` / `source_hash` が JSON で `playlistsync` / `sourcehash` になっていた）
- P5-1 からの持ち越しのうち、Derived の欠損と `compute` の 1 トランザクション化は解消した
- P5-3 / P5-4 へ持ち越し: プレイリスト操作の順序（削除を先に）と改名の 2 段 / エラーのプレイリストが古い写しと衝突する場合 / agent のプレイリストの dest_path / プレイリストのパス長とトラックの `.spindle` 予約名。加えて `has_open_work` が `device_sync` の payload の `$.device_id` を前提にしていること（P5-3 で合わせる）

### P5-3a で決めたこと（2026-09-30）

- 実機の spike（P5-0）は後回しにし、端末の操作を `DeviceFs` trait に閉じ込めて偽の端末 FS と偽の adb で
  先に作った。実機に依存する挙動（shell v2 の stdin、toybox の `find` / `stat` / `sha256sum`、Poweramp の
  レシーバと extras）は `#[ignore]` の実機テストと定数に閉じ込め、P5-3b で Xperia を繋いで固定する
- adb のサブコマンドは `shell` だけを使う。shell v2 は pty を割り当てない限り stdin / stdout がバイナリ
  安全で終了コードも返る。`exec-in` / `exec-out` は終了コードを返さず `No space` を取りこぼす
- バッチ以外の意図は `put` と `rm` だけ。パス変更は必ずバッチに入れる。バッチのメンバーは曲だけで、
  プレイリストの改名は旧パスの削除を全部先に行ってから新パスへ書く（中身は毎回生成し直すので失うものが無い）
- 失敗した操作には `done` を書かない（`done` の付いた `put` は回復で sha256 を見ずに反映済みとみなす）。
  `done` は次の意図と同じ追記に載せ、manifest の書き直し（圧縮）は完了 50 件ごとと同期の最後に行う
- 回復は `prepared` 以前のバッチを縮めずに破棄する（`batch_abort` を耐久化してから `new` を消す）。
  同期の実行中に準備で失敗したメンバーが出たときだけ、その場で成分ごとに縮める
- 実ファイルが無い・サイズが違う曲は、回復の結果でトークンを空にして差分に「更新」として出す
  （manifest から外すと管理外になって削除できなくなる）
- パス変更のバッチの一時ファイル（`staging` / `new`）の名前に `batch_id` を含める
  （`.spindle/moving/<batch_id>-<op_id>`、`.new`）。縮めた後の新バッチが中止済みの旧バッチと同じ名前を
  使うと、回復が旧バッチの掃除として新バッチの `new` を消してしまうため
- 回復はバッチのメンバーの位置を、仕様の表どおりファイルが在るかどうかで判定する（`staging` に在れば
  空け済み、`src` に在れば置く、無くて `to` に在れば置き済み）。sha256 の一致で判定すると、同じサイズで
  外部から書き換えられた曲で入れ替えが壊れる。内容の食い違いはサイズの照合と「内容を検証」に任せる
- 置き先を manifest に無いファイル（手で置いたもの）が占めていれば上書きしない。同期の開始時に一覧を
  1 回取り、その曲・プレイリストは「管理外のファイルと衝突」のエラーで保留する。パス変更では、その曲を
  含む成分を全員外す
- 置き先を別の管理下の曲・プレイリスト（manifest にある別の id）が占めていれば、意図を書かずに
  「パス衝突（移動しなかった曲が置き先にいる）」のエラーで保留する。差分は移動中の曲の今のパスを「空く」と
  扱うので、その移動が実行されない（行き先が管理外・準備の失敗で縮んだ・再開時に外れた）と、追加が移動しな
  かった曲を上書きし、manifest のパスが重複して以後の回復が必ず失敗するため。manifest の書き出しも読み込みと
  同じ検査（件数・id とパスの一意性・パスの範囲）を通し、壊れた正本を書かない
- 回復は、ジャーナルのバイト列が空でなければ（読めるレコードが 0 件の切れた断片だけでも）圧縮する。
  また、自分が追記する前に末尾の切れた断片を落としたジャーナルに差し替える（tmp + `mv -f`）。断片を残すと
  次の追記が断片と 1 行に連結され、その意図が消えるか、さらに次の追記で全体が読めなくなるため
- 回復が実ファイルの無い・サイズの違う項目に付ける `STALE_TOKEN` は、結果の中だけでなく manifest にも
  書く（トークンが変わった項目が 1 件でもあれば、ジャーナルが空でも圧縮する）。同期は回復した manifest から
  始めるので、今回の計画に入らなかった項目のトークンが同期の結果で元に戻ってしまうため
- 「内容を検証」は回復済み（ジャーナルが空）の正本に対してだけ行う。ジャーナルが空でなければ失敗させる
  （検証の書き直しの圧縮で未完了の意図を捨てないため）
- 「内容を検証」で食い違った・無くなった曲は、manifest から外さずトークンを空（`STALE_TOKEN`）にする。
  外すと実ファイルが管理外になり、上の規則で上書きできなくなるため。次の差分で「更新」に戻る
- adb の未接続は、adb クライアント自身の文言（行頭の `adb: device '…' not found`・
  `error: device offline` など）だけで判定する。端末側のスクリプトの `…: not found` を未接続と
  取り違えないため
- 端末の一覧（`list_files`）は、1 件でもサイズを取れなければ全体を失敗させ、同期・回復も書き込みの前に
  失敗させる。握り潰すと手置きのファイルが一覧から消えて管理外と分からず、上書きしうるため。列挙の後に
  消えたファイルでも失敗するが、同期が失敗するだけで次回やり直せる（上書きの危険より安全側）。失敗は終了コードに
  頼らず出力でも伝える: 先に `find | wc -l` で数えた件数を `N <件数>` で書き、`find -exec stat -c '%s %n' {} +` が
  0 で終わったときだけ（root が無い経路でも）終端の印 `END` を書く。終端が無い・終端の後に続きがある・形の
  崩れた行がある・件数と行数が合わない出力は失敗とする（find が stat の失敗を終了コードに伝えなくても、欠けた
  一覧を完全な一覧と読まないため）。ファイルごとに stat を起こす形は実機で遅すぎたので改めた（「実機での確認」）
- プレイリストの書き込み（追加・更新）が成り立つかは、旧パスを消す前に全操作について判定する。中身が無い・
  行き先が管理外のファイル・行き先を今回空かない別の管理下の項目が占める操作は、旧パスも消さずに丸ごと保留
  する（保留になった改名の旧パスは空かないので、そこへ来る改名も保留になる。不動点まで繰り返し、入れ替え・
  循環は通す）。旧パスを先に消すと、保留のときに残すべき既存の写しを失うため
- 確定済みの計画の再開で、プレイリストの改名（更新・from ≠ to）が今の状態に行が無く（旧パスの削除が済んだ）、
  今の差分に同じ id・同じ行き先・同じトークンの追加があれば、「旧パス削除済みの正当な中間状態」として、計画の
  `op_id` のまま追加として実行する。外すと同じ計画の再開が新パスを書かずに成功扱いになり、次の計画を確定する
  までプレイリストが欠落するため。曲のパス変更はバッチで原子的に完遂されるので同様の中間状態は無い
- 却下: 追記ごとに `sync` を 2 回（意図と完了）打つ。1 曲あたりの adb 呼び出しが増え、初回の全曲転送で
  数時間の差になる。完了は次の意図と一緒に耐久化しても、回復が sha256 で判定できる
