## D-105 id の再利用は、GC が `tracks` の最大 id の行を消さないことで防ぐ

**背景**（2026-10-14）: `tracks.id` / `playlists.id` は `INTEGER PRIMARY KEY` で `AUTOINCREMENT` ではない。SQLite は次の行に `max(rowid)+1` を振るので、GC が最大 id の行を消すと次に入る曲が同じ id を得る。端末の写し（`device_items`、Android の manifest、Mac のエージェントの state）は `track_id` で曲を指すので、7 日以上同期していない端末では差分が `UpdateMove` になる。Android は正しく収束するが、Mac ではミュージック.app の track を保ったまま location を付け替える（D-101）ので、再生回数・レート・追加日が別の曲に移る（D-102 の 4、D-103）。

**決定**:

1. **GC は `tracks` の最大 id の行を消さない**。`db::gc::missing_tracks`（一覧。`/api/gc/preview` の件数もここから）と `delete_tracks`（削除の SQL の再確認）の両方に `id < (SELECT max(id) FROM tracks)` を足す。計画の後に曲が増えても減っても、削除の時点の最大で判断する
2. 残した行は missing のまま残る。後で新しい曲が入れば最大でなくなり、次の GC で消える。その id は最大より小さいので二度と振られない。残した行のアルバム・Derived・アートワークは既存の「参照があれば消さない」で残る（最大 1 曲分）
3. **プレイリストの id の再利用は受け入れる**（D-103 のとおり。差分は改名の `Update` として収束し、失う情報が無い）
4. **古いバックアップへの復元は対象外とし、手順で扱う**。復元した DB は採番も巻き戻るので（`AUTOINCREMENT` でも `sqlite_sequence` ごと巻き戻る）、バックアップより後に足した曲に起動時スキャンが振る id は別の曲に当たり得る。端末の行と認証はバックアップの時点のまま戻るので、引き継ぎは自動では促されない。復元の手順（`docs/OPERATIONS.md`「端末は引き継ぎし直す」、SPEC §14「バックアップ」）に、同期する前に端末を削除して引き継ぎし直す（Android は「前の登録の保存先」、Mac は `pair --adopt`）と書く。消す前に名前・形式・送る範囲を控えて同じ設定で作り直す（追加の既定は「印のプレイリスト」で、元が「全曲」なら引き継いだ全曲が削除になり、Mac ではミュージック.app の track ごと消える）。範囲が分からなければ「全曲」（Library にある曲を端末から消さない）。引き継いだ後の最初の差分に予期しない削除があれば確定しない。codex のレビューの指摘

**理由**: DB の中で再利用が起きるのは最大 id の行を消したときだけで、その 1 行を残せば十分。スキーマも、差分も、端末の手順も変えずに済む。復元は稀な手作業の操作で、引き継ぎ（D-103 / D-104）が既にあるので、手順に 1 段足せば済む。

**却下**:
- `tracks` を `AUTOINCREMENT` に移すマイグレーション: SQLite では表の作り直しになり、FTS5 の external content・トリガー・外部キーの参照元を巻き込む。得るものが上の 1 行と同じ
- token・sha256・パスがすべて違う既存の写しを `Update` ではなく Delete + Add にする: Library で一括にタグを直して改名するのは正当な日常操作で、そのたびに Mac の再生回数が消える
- 最大 id を別表に持って挿入時に振る: 別表も DB の中なので復元で巻き戻り、DB の中の再利用は最大 id の行を残すだけで防げる
- 最大 id を DB の外のファイルに記録し、スキャンがそれより上から振る（復元でも巻き戻らない）: DB の外に正本を 1 つ増やす。データセットごと ZFS のスナップショットへ戻すと両方巻き戻るので、手順の案内はどのみち要る。復元は稀なので手順で扱う
- 復元を検出して端末に引き継ぎを強制する: 検出に DB の外の記録が要り、上と同じ
