# ブラウザからのアップロード（購入音源の取り込み）設計

> 作業中だけ置く設計書。実装後に要点を `docs/spec/` へ、判断を `docs/decisions/D-116.md` へ移して消す。
> モックで合意した画面: 入口は A（ナビにタブ）、流れは 1（送ってから分け方を確かめて Inbox へ置く）。

## 1. 目的と背景

ダウンロード購入した音源（mora などのハイレゾ FLAC。ときどき MP3 / AAC しか売っていないものもある）を
ブラウザから spindle に入れたい。今は CD（吸い出し）と YouTube（ytdl）しか入口が無く、購入音源は一度も
入れられていない（SPEC §5 のレイアウトは「Inbox/（ハイレゾ購入分などをここへ置く）」と書くが、置く手段が無い）。

既存の取り込みはどちらも「Inbox にディレクトリを組み立てて公開 → `inbox` ジョブ → 承認画面 → 配置」という
同じ流れに乗っている。アップロードもこの流れに合わせ、**Inbox に置くところまで**を新しく作る。承認・配置・
後続（RG / 変換 / 端末）は今のものをそのまま使う。

### 使われ方（ユーザから聞いたこと）

- 届く形は zip のことも、ファイルそのまま（zip でない）のこともある。両方受ける。
- 1 回の量は基本アルバム 1 枚分。ハイレゾはシングル 1 曲単位で買うので、**ばらばらのシングル数枚を
  まとめて**入れることも多い。
- 形式は FLAC（ハイレゾ）が主で、MP3 / AAC もある。
- 操作は **PC のブラウザだけ**（スマホ版には置かない。§12.7 の「取り込みは PC」と同じ）。

## 2. ゴール / 非ゴール / 失敗とみなすこと

ゴール

- zip・音声ファイル・フォルダのどれをドロップしても、アルバム（タグ）ごとに Inbox の件へ分けて置ける。
- Inbox に入れる**前に**分け方と注意（ライブラリに同じ音声がある等）を見て、まとめる / 外すができる。
- 購入音源に付いてくるブックレット PDF や追加の画像も、ライブラリのアルバムのフォルダへ一緒に持っていく。
- 外（Cloudflare Tunnel 経由）からでも数 GB のハイレゾアルバムを送れる。

非ゴール

- ストアの API 連携・自動ダウンロード（購入はユーザがブラウザで行い、落としたファイルを渡す）。
- スマホからのアップロード。
- 承認画面の作り直し（出どころの表示に「アップロード」を足すだけ）。
- Inbox の件同士を後からまとめる操作（まとめるのはアップロード画面の ③ で済ませる）。
- 送信の中断からの**ファイル途中からの**再開（途中のファイルは送り直し。下記 §5.2）。

失敗とみなすこと（動いても差し戻す）

- アップロードしたファイルが承認を経ずに Library へ入る。
- 送信途中・展開途中の不完全なディレクトリが Inbox の件として見える（走査に拾われる）。
- 送ったまま放置したものが際限なく溜まる。
- zip の中身でパスの境界を越える（`../`、絶対パス、symlink）。

## 3. 全体の流れ

```
[① ファイルを選ぶ] ドロップ / ファイル選択 / フォルダ選択
   ↓ 選んだ時点で送信開始（確認を挟まない）
[② 送信]          ファイルを分割して送る（Cloudflare の 1 リクエスト 100MB 上限）
   ↓              サーバは Inbox 直下の隠しディレクトリ（ステージング）に書く。zip は届いたら展開
[③ 分け方]        サーバがタグを読み、件（アルバムアーティスト + アルバム）に分けて状態付きで返す
   ↓              人が まとめる / ファイルを外す / 件を外す
[④ Inbox へ置く]  件ごとに Inbox/upload/<albumartist>/<album>/ へ rename で公開 → inbox ジョブ投入
   ↓
[⑤ Inbox で承認]  置いた件を並べ「Inbox で開く」（YouTube の ④ と同じ）
   ↓
既存: 承認 → 配置 → RG → opus / aac → 端末
```

## 4. 画面（アップロードタブ）

### 4.1 置き場所

- ナビ: `ライブラリ / アルバム / CD / YouTube / アップロード / Inbox / 端末`。CD・YouTube と並ぶ入力の 1 つで、
  右隣の Inbox に数字が増える、という今の導線（§12.1）に乗る。左サイドバーは畳む（CD / YouTube と同じ）。
- スマホ版には出さない。
- 段は `components/Step.tsx` の番号付きの段（CD / YouTube / Inbox と同じ見た目）。

### 4.2 各段

**前回の続き**（段の上の帯）: Inbox へまだ置いていないアップロードがあれば
「前回の送信で Inbox へまだ置いていないものがあります（日時、N 件 M 曲）」と「続きを開く」「捨てる」。
続きを開くと ③ から再開する。複数あれば新しい順に並べる。

**① ファイルを選ぶ**: ドロップ欄と「ファイルを選ぶ」「フォルダを選ぶ」。受ける形式の一覧を小さく出す
（FLAC / WAV / ALAC / AIFF / MP3 / AAC(m4a) / Opus、zip）。選んだ（ドロップした）時点で送信を始める。
送信中・③ を表示中でも追加でドロップでき、同じアップロードに足される（③ を取り直す）。

**② 送信**: ファイル（zip は zip 1 つ）ごとに進捗バーとバイト数。zip は送り終えたら「展開中」→「展開済み」。
失敗したファイルは理由と「再送」。送信中に画面を離れても、送り終えたファイルはサーバに残る
（途中のファイルは捨てて送り直し）。送信中はブラウザの離脱確認を出す。

**③ Inbox での分け方**: 件の表。列は チェック / 件（アルバムアーティスト — アルバム）/ 曲数 / 形式 / 状態。
件は ▸ で開くとファイルの行（チェック付き）と同梱ファイルを見せる。

- 状態（1 件に複数当たれば強い順に 1 つ出し、残りは開いた中に）:
  - `同じ音声がライブラリにある`（赤。**初期でチェックを外す**）: 件の全ファイルの音声がライブラリの
    active な行と一致。開いた中に一致したライブラリのパス。一部だけ一致なら件は他の状態のまま、
    一致したファイルだけ赤で初期チェックを外す
  - `Inbox に同じ件がある`（黄）: 置き場所 `upload/<albumartist>/<album>/` が Inbox に既にある（公開すると
    ` (2)` の別の件になる）。Inbox の他の件との音声の一致は見ない（`inbox_files` に音声の指紋が無く、
    Inbox の実体を開いて計算するのは重いため。設計者の判断）
  - `ライブラリの『…』（N 曲）に追加`（青）: 既存の album への追記先が見込まれる（承認画面の `destination` と同じ規則）
  - `Inbox で名前を入れる`（黄）: アルバム名のタグが無い件
  - `新規`（緑）
- 音声でも同梱ファイルでもないもの（`readme.txt`、`__MACOSX/`、`.DS_Store` 等）は表の末尾に
  「取り込まない: …」と 1 行で出す（置かない）。
- 操作: 件のチェック、ファイルのチェック、「選んだ件を 1 件にまとめる」（2 件以上チェックしたとき。
  まとめた件の名前は先頭の件のもの。承認画面で直す）。
- 分け方と除外の状態はサーバに保存する（「前回の続き」で同じ状態から開ける）。
- zip の中で拒否したエントリ（`../`・絶対パス・symlink・大小文字だけ違う同名など）は、その zip の行の下に
  「取り込めなかった: <名前>（理由）」と出す。zip が壊れている・暗号化されているなら zip 全体を失敗にして
  理由を出す。
- 曲が 1 曲もチェックされていない件はチェックできない（公開すると Inbox に現れないため）。

**④ Inbox へ置く**: 「N 件 M 曲を Inbox へ置く」と「送ったものを捨てる」（確認ダイアログ）。押せるのは
送信と展開がすべて終わり、チェックの入った件が 1 件以上で、その全件に曲が 1 曲以上チェックされているとき。
押した後は ③ の変更も「捨てる」もできない（公開が終わるまで）。展開中も「捨てる」は押せない。

**⑤ Inbox で承認**: 置いた件を並べ、「Inbox で開く」でその件を選んで Inbox を開く（YouTube の ④ と同じ
挙動: 一覧にまだ無ければ現れるまで待ち、人が別の件を選んだらやめる）。

### 4.3 Inbox 側の変更

- 承認画面 ① の出どころに `アップロード`（`lib/inbox.ts` の `itemSource` に `upload/` を足す）。
  サイドカーの記録から「アップロード日時、元のファイル名（zip 名）」も出す。
- 同梱ファイル（PDF・追加画像を含む）を ① に一覧で出す（「ライブラリのアルバムのフォルダへ一緒に移す」）。
- 承認・配置の手順は変えない。

## 5. サーバ

### 5.1 ステージングとマニフェスト

- 置き場所は **Inbox 直下の隠しディレクトリ** `.spindle-upload-<id>/`（CD の `.spindle-rip-<DiscID>` と同じ
  考え方。Inbox の走査は全階層で `.` で始まる名前を飛ばすので件に見えない。公開を同じデータセット内の
  ディレクトリ rename にできる）。`<id>` は 16 桁の hex。
- **状態の正はマニフェスト** `.spindle-upload-<id>/upload.json`（tmp + fsync + rename で書く）。DB に表は
  作らない（不変条件 1。DB を消してもマニフェストと実体から一覧・再開ができる）。マニフェストが持つもの:
  - 送ったものごとの **origin**（`o1`, `o2`, …。アップロード内で一意な安定 ID）: 種類（音声 / zip / その他）、
    ブラウザ上の元の相対パス（フォルダ選択なら `Album/01.flac`、zip なら `mora.zip`）、宣言サイズ `total`、
    受け取ったバイト数 `received`、状態（受信中 / 完了）、人が外したか（`removed`。外した origin は件には入れないが、
    実体が GC で消えるまでは予算に数える）、実体が食い違って壊れたか（`damaged`）
  - zip の origin はさらに: 成功した展開の世代 `generation`（0 = 未展開）と次に使う世代の番号 `next_generation`
    （予約のたびに進めて永続化するので、失敗した世代の番号を使い回さない）、成功した世代で書いたバイト数、
    展開中の世代の番号（物理的なバイト数はその世代の `garbage` の項で数える）、拒否したエントリの一覧（名前と理由）、
    zip 全体の失敗（理由と、やり直せる失敗か = 空き不足・I/O・取り消し / やり直せない失敗か = 壊れた・暗号化・
    上限超過）
  - ③ の変更（まとめた件のキーの組、外したファイル・件、初期で外れるものを入れ直した記録）
  - 公開計画（§5.5。公開を押した時点で凍結）、`publish_requested_at`、Inbox の走査を投入した時刻
    `inbox_enqueued_at`、`discarded_at`、`created_at`、`updated_at`
  - 古くなった・失敗した展開世代など、GC に消させるステージング内のディレクトリの一覧 `garbage`（パス、
    バイト数、載せた時刻。消えるまで予算に数える）
- 実体のレイアウト（すべて origin ID で分けるので、利用者の名前どうしが置き場所で衝突しない）:
  - `files/<origin>.part` → 完了で `files/<origin>`（音声・その他のばらのファイルは origin ID の名前で置く。
    元の名前と相対パスはマニフェストにある）
  - `zips/<origin>.zip`（zip 本体。公開か破棄まで残し、GC が消す。ディスクは一時的に 2 倍使う）
  - `x/<origin>/g<generation>/…`（zip の展開先。中は zip 内の相対パスのまま）
  - `publish/<n>/`（公開の組み立て。§5.5）
- **マニフェストの読み書きはアップロードごとに直列にする**（プロセス内の `upload_id` ごとの非同期 mutex。
  同時 2 本の送信・PATCH・展開・公開・GC が同じマニフェストを読み書きしても更新を失わない）。これは
  ライブラリのファイルの排他ロックではない（SMB の他プレイヤーと共有しない、spindle だけのステージング）。
- マニフェストの無い・読めない `.spindle-upload-*` は「壊れたアップロード」として「前回の続き」に出し
  （捨てるだけできる）、勝手に消さず、上書きもしない。
- パスの検証: ブラウザの相対パスと zip のエントリ名は SPEC §5 のパス規則（`RelPath::parse`）で検証する。
  `\`・`..`・絶対パス・制御文字・空要素・`.` で始まる要素は拒否（`\` を `/` に読み替えない）。zip の
  symlink・特殊ファイルのエントリは捨てる。書き込みは root の dirfd から openat2
  （`RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`）。名前の比較は `rel_path_key`（casefold + NFD）。
- 受ける音声の拡張子はアップロード専用の許可リストで固定する: `flac` `wav` `m4a` `aif` `aiff` `mp3` `opus`
  （画面の表示と同じ）。それ以外は「取り込まない」。

### 5.2 送信（分割）

- 外からは Cloudflare Tunnel（無料プランは 1 リクエスト 100MB 上限）→ Nginx Proxy Manager を通るので、
  ファイルは**チャンク（32 MiB）に分けて順に送る**。最初のチャンクで origin を作り、宣言サイズを
  マニフェストに記録する（この時点で予算に算入。下記）。
- 1 チャンクの処理: マニフェストの鍵を取り → `.part` の実際の大きさが `offset` と一致するか確かめ（不一致なら
  409 と実際の大きさを返す。**`.part` の大きさが正**で、マニフェストの `received` は表示用の写し）→ 追記して
  fsync → `received` を更新。最後のチャンクで大きさを確かめ `.part` を正式な名前へ rename → 完了を記録。
  電源断でマニフェストが実体より遅れても、次の要求と一覧・単体の取得で実体に合わせる: 未完の origin で
  `.part` があればその大きさを `received` に、`.part` が無く正式な名前のファイルがあり大きさが `total` と
  一致すれば完了に進める（rename の後・マニフェストを書く前に落ちた場合）。両方ある・大きさが合わないなどの
  食い違い（普通の停止では起きない外部の変更・破損）は origin を `damaged` にして「壊れた。外して送り直す」と
  出す（同じパスをドロップし直すと新しい origin で送る。壊れた実体は GC まで残る）。
- 再開: 途中のファイルは画面で「再送」すると最初から送り直す（`offset = 0` で `.part` を作り直す）。
  前回の続きを開いたとき、未完のファイルは「送信が途中で止まった」と出し、同じファイルをドロップし直すか
  外すかを選ばせる（ブラウザはファイルの中身を覚えていないため）。ドロップし直すと、同じ相対パスの未完の
  origin を使って最初から送り直す（新しい origin を作らない）。「外す」は origin に `removed` を付ける。
- 同時に送るファイル数は 2。
- **予算はアップロード全体で数える**: 宣言サイズの合計（受信中を含む。外した origin も実体が残る間は含める）+
  全 zip の成功した世代で書いたバイト数 + `garbage` のバイト数（展開中の世代もここで 1 度だけ数える）、が
  `[upload].max_upload_bytes` を超えるなら断る（413）。展開は**次に書くブロック（8 MiB）を鍵の中で先に予約して
  から**書くので、送信と展開が同時に走っても合計で上限を守る（予約が実際より多いぶんは安全側の誤差）。1 ファイルは `max_file_bytes` まで。
  受ける前と展開の途中（一定バイトごと）に Inbox データセットの空き容量を確かめ、足りなければ断る（507）
  / 展開を失敗にする。

### 5.3 zip の展開

- zip を受け取り終えたら `upload` ジョブ（op = unpack）を投入する。展開は `next_generation` を進めて予約した
  **新しい世代** `x/<origin>/g<N>/` へ書き、成功したらマニフェストの成功した世代を切り替える（1 回の書き込み）。
  古い世代と失敗した世代は `garbage` に入れ、物理削除は GC に任せる（展開先を「先に消す」ことはしない）。
  成功した zip の展開ジョブが再実行されたら何もしない。展開中の世代を残したまま止まっていた（再起動で
  ジョブが再実行された）ら、その世代は再開できないので `garbage` に残したまま捨て、新しい世代で最初から展開する。やり直せる失敗は画面の「展開し直す」で、やり直せない
  失敗はその zip を「外す」ことで先へ進める（外さず公開はできない）。
- 取り消しと予算は、エントリごとではなくコピーのバッファごとに確かめる（巨大な 1 エントリでも止まる）。
  UTF-8 として読めないエントリ名はそのエントリだけ拒否する。
- エントリごとの規則: パス規則に外れる・symlink・特殊ファイル・`rel_path_key` が先のエントリと衝突・
  ファイルとディレクトリの衝突は**そのエントリだけ拒否**して一覧に記録し、展開は続ける。`__MACOSX/` 以下は
  展開しない。中央ディレクトリが壊れている・暗号化されている・対応しない圧縮方式は zip 全体を失敗にする。
  エントリ数が `max_zip_entries` を超える、または書いたバイト数（ヘッダの申告を信じず実際に書いた量）が
  予算を超えたら zip 全体を失敗にする。
- 展開とジョブの間の取りこぼし: 起動時と一覧・単体の取得時に**照合**（reconcile）を走らせ、完了していて未展開
  （失敗していない）の zip、公開を要求済みで終わっていないアップロード、全件公開済みで Inbox の走査をまだ投入して
  いないアップロードについて、active なジョブ（dedup キー）が無ければ投入し直す。
  DB が消えても、ジョブを投入する前に落ちても、ここで拾える。

### 5.4 分け方（③ の計算）

- 送り終えた音声（ばらのファイルと、展開済みの世代の中身）のタグを読み（lofty。Inbox の走査と同じ読み取り）、
  件のキーを決める:
  1. ALBUMARTIST（無ければ ARTIST の先頭値）+ ALBUM（`canonical_key` で比較）が揃えばそれで 1 件
  2. ALBUM が無いファイルは、**同じ zip / 同じフォルダから来たもの同士で 1 件**（zip は origin、フォルダ選択は
     元の相対パスの最初の要素）。ばらで送ったファイルで ALBUM が無いものは 1 ファイル 1 件
- 状態の判定（§4.2）:
  - ライブラリに同じ音声: Inbox の `self_candidates` と同じく `audio_md5`（FLAC の STREAMINFO MD5）/
    `audio_fp`（非可逆のパケット列ハッシュ）で active な行を引く
  - Inbox に同じ件: 置き場所のディレクトリが Inbox にある
  - 追記先: Inbox の `destination_of` と同じ規則を下書き相当の値で引く
- 同梱ファイル: 件の曲と同じディレクトリにある同梱ファイル（§5.6）を件に付ける。どの件の曲とも同じ
  ディレクトリにない同梱ファイルは、件が 1 つならその件に、複数ならどの件にも付けず ③ で「どの件にも付けない
  同梱ファイル」として出す（人が付け先を選ぶ UI は作らない）。
- **件のディレクトリは平ら**にする。Inbox の走査は「音声のあるディレクトリ 1 つ = 1 件」で、配置が持っていく
  同梱ファイルも件のディレクトリ直下だけなので、`Disc 1/` `Disc 2/` や `Booklet/` `Scans/` のようなサブフォルダは
  件の直下へ集める（タグで同じアルバムなら複数枚組も 1 件になる）。集めて名前が `rel_path_key` でぶつかったら、
  元の親フォルダ名を前に付けて `Disc 2 - 01 Track.flac` のように別名にし、③ の開いた中に「名前を変えて置く:
  元 → 新」と出す（音声の Inbox 上の名前は配置でテンプレートの名前になるので一時的なもの。同梱ファイルは
  この名前のまま Library へ行く）。それでもぶつかれば拡張子の前に ` (2)` を付ける。

### 5.5 Inbox へ置く（公開）

- 「Inbox へ置く」を押すと、その時点の分け方から**公開計画を作ってマニフェストに凍結**し、`upload` ジョブ
  （op = publish）を投入する。計画は件ごとに: 件のキー、全メンバーの元の場所（ステージング内）と置く名前、
  段階。以後 ③ の変更と「捨てる」は受け付けない。押し直し（二度押し・再起動後）は冪等に同じ計画のジョブを
  投入し直すだけ。
- 公開の段階（件ごと。各段階の後にマニフェストを書く。再実行は計画と実体だけで続きから進める）:
  1. **組み立て**: `publish/<n>/` へメンバーを `RENAME_NOREPLACE` で移す（元に無く `publish/<n>/<名前>` に
     あるものは移し済み）。サイドカー `spindle-inbox.json` に `upload` の記録（アップロード id、件のキー、
     日時、元の名前）を書き、ディレクトリを fsync → 段階を「組み立て済み」
  2. **宛先の確定**: `upload/<albumartist>/<album>`（`sanitize_component`。アルバム名なしは
     `upload/_untitled/<zip 名かフォルダ名>`）、既にあれば ` (2)`, ` (3)` … の最初の空き名を選び、**宛先を
     マニフェストに書いてから** rename する（段階「公開中（宛先）」）
  3. **公開**: 宛先の親を作り `publish/<n>/` を宛先へ `RENAME_NOREPLACE` → 親を fsync → 段階「公開済み」
  - 復旧: 「公開中」で `publish/<n>/` が無ければ rename は済んでいる（宛先が既に Inbox の配置で消えていても
    よい）ので「公開済み」にする。`publish/<n>/` が残り宛先が空いていれば rename をやり直す。宛先が他に
    取られていれば 2 からやり直す。
  - 全件「公開済み」になったら `inbox` ジョブを投入し、**公開より後に走る走査を確保できたときだけ**
    `inbox_enqueued_at` と `discarded_at` を入れる。新しく投入できた・待ち（queued）の inbox ジョブがあるなら確保できて
    いる。実行中（running）の inbox ジョブと重なったら（既に走査を終えて新しい件を見ないかもしれない）、記録せず
    公開ジョブを数秒後にやり直させ、そのジョブが終わってから投入する。記録の前に落ちても照合が投入し直す。外したファイル・件・取り込まない
    ファイルはステージングに残り、GC が `[gc].retention_days` 後に消す。
- 曲が 1 曲もない件は計画に入れない（API が 400。Inbox に現れない件を作らない）。
- ジョブは各段階の前に `discarded_at` を確かめる（捨てたものは公開しない。ただし公開要求後は捨てられない）。

### 5.6 同梱ファイルの拡張

- `crate::cd::riplog::is_companion_name` に **PDF（`*.pdf`）と画像（`*.jpg` / `*.jpeg` / `*.png` / `*.webp`）**を
  足す。今これを使うのは Inbox の配置、却下した件の削除（GC）、一括リネームの同梱ファイルの追随の 3 か所で、
  どれも足した形式に同じ規則で効く（CD・手置き・YouTube の件も同じ。既に却下済みの件の PDF・画像も削除の
  対象に入る）。
- アートワークの選び方（`cover_rank`）は変えない（ジャケットの選択は今と同じ）。

### 5.7 ジョブ・API

- ジョブ種別 `upload`（並列 1、op = unpack / publish。どちらも冪等で、再起動で `queued` に戻ってやり直せる）。
  `jobs` の CHECK に足すため新しいマイグレーションで表を作り直す（0005 と同じ手順）。
- `POST /api/uploads` → 作る / `GET /api/uploads`・`GET /api/uploads/:id` → 状態（③ の分け方と状態を含む。
  照合もここで走る）/ `POST /api/uploads/:id/origins { path, total }` → origin を作る / `PUT /api/uploads/:id/origins/:origin?offset=` → チャンク / `PATCH` → 分け方の
  変更（origin を外すを含む）/ `POST …/origins/:origin/unpack` → やり直せる失敗の zip を展開し直す /
  `POST …/publish` → 公開（冪等）/ `DELETE` → 捨てる（論理削除）。
- 展開中・公開要求後の `DELETE` と `PATCH` は 409（実行中の処理と捨てるが競合しない）。
- CSRF は既存の規則（`Origin` 完全一致 / `Sec-Fetch-Site`）。`DefaultBodyLimit` はチャンクの上限 + α。

### 5.8 GC

- 対象: (a) `discarded_at` から `[gc].retention_days` 経ったステージング（公開後の残り・捨てたもの。zip 本体・
  `.part`・古い展開世代もここで消える）、(b) マニフェストの無い・読めない・捨てる印の付いたステージングで
  ディレクトリの mtime から `retention_days` 経ったもの、(c) `garbage` に載ったステージング内のディレクトリ
  （アップロードが生きていても、古い展開世代は `retention_days` 後に消す）。
- 放置: 公開も破棄もされず最後の操作から `[upload].stale_days`（既定 30）経ったアップロードは、GC が
  `discarded_at` を入れる（消すのは (a) の規則で後日）。「前回の続き」の帯に期限を出す。
- 既存の Inbox GC（D-90）と同じく、計画時の根拠（id、`updated_at`、`discarded_at`、ディレクトリの stat）を
  持ち、**消す直前にアップロードの鍵を取って読み直し**、根拠が変わっていれば消さない（計画の後に再開・更新
  されたものを消さない）。ステージング全体を消すときは鍵だけを取り（マニフェストを書き戻さない）、`garbage` の
  世代を消すときはマニフェストから外して書き戻す。GC 以外は物理削除しない。

## 6. 不変条件との関係

- ファイルが正: 件の情報はサイドカー、アップロードの状態はマニフェストと実体が正（DB に表を持たない）。
  ジョブ行が消えても照合が投入し直す。
- 物理削除は GC のみ（捨てる・外す・放置は論理削除）。
- 承認を経ずに Library へ入らない（公開先は Inbox）。
- ライブラリのファイルを排他ロックしない（マニフェストの直列化は spindle 内だけのステージングに対するプロセス内の鍵）。
  ジョブは冪等（展開は世代を切り替え、公開は凍結した計画と段階で続きから進む）。
- 非可逆 → 非可逆の再エンコードはしない（MP3 / AAC はそのまま置く）。

## 7. 作る側に任せること（私の判断として置いたもの）

- チャンクの大きさ（32 MiB 案）、同時送信数、サイズ上限の既定値。
- 放置したアップロードを破棄待ちにする期間（30 日案）。
- API とジョブの名前・形、表の列。
- ばらで送った画像・PDF の付け先が決まらないときの扱い（どの件にも付けずに出すだけでよい）。
- ③ の状態の色と文言の細部（モックに沿う）。

設計者（Claude）の判断として入れたもの（ユーザ確認の対象）:

- サブフォルダは件の直下へ平らに集め、名前がぶつかればフォルダ名を前に付ける（§5.4）。
- 状態の正はステージングのマニフェスト `upload.json`（§5.1、不変条件 1）。
- zip 本体は公開か破棄まで残し、GC が消す（§5.1、§5.8）。
- 同梱ファイルに PDF と画像を足し、アップロード以外の件にも同じ規則を当てる（§5.6）。
- 置き場所の名前が既にあるときは ` (2)` の別ディレクトリにして既存の件に混ぜない（§5.5）。
- 「Inbox に同じ件がある」は置き場所の名前だけで判定し、Inbox の他の件との音声の一致は見ない（§4.2）。
- zip の危ないエントリはそのエントリだけ拒否して続け、壊れた・暗号化された zip は全体を失敗にする（§5.3）。
- 展開中・公開要求後は「捨てる」と ③ の変更を受け付けない（§5.7）。
