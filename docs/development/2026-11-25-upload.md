# ブラウザからのアップロード 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** zip・音声ファイル・フォルダをブラウザから送り、タグのアルバムごとに Inbox の件として置けるようにする（承認以降は既存のまま）。

**Architecture:** 送ったものは Inbox 直下の隠しディレクトリ `.spindle-upload-<id>/` に origin ID の名前で置き、状態の正はその中の `upload.json`（DB に表は作らない。読み書きはアップロードごとにプロセス内の鍵で直列化）。zip の展開（世代を切り替える）と Inbox への公開（凍結した計画を段階で進める）は新しいジョブ種別 `upload`。ジョブの取りこぼしは照合（reconcile）が投入し直す。分け方（件・状態）はマニフェストと実体から毎回計算する純粋関数。画面はナビの新しいタブ「アップロード」。

**Tech Stack:** Rust（axum / rusqlite / lofty / 新規 `zip` クレート）、React + TypeScript（vitest / oxlint）

**Spec:** `docs/development/2026-11-25-upload-design.md`（以下「設計」。§番号は設計の節）

## Global Constraints

- CLAUDE.md の不変条件・禁止事項・コーディング規約がすべて掛かる（非テストで `unwrap`/`expect`/`panic!` 禁止、生 SQL 組み立て禁止、`db/migrations` の既存ファイルを書き換えない、`cargo clippy -- -D warnings` / `cargo fmt --check` / `cargo test` / `npx vitest run` / `npm run lint` が通る）。
- ファイルは Inbox の `RootDir`（openat2 `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`）経由でだけ触る。パス文字列を結合して `File::open` しない。
- 名前の比較・一意性は `canonical_key`（= `rel_path_key`。casefold + NFD）。
- **物理削除は GC だけ。** アップロードのコードは unlink / rmdir をしない（`.part` を `offset = 0` で作り直すときの `O_TRUNC` だけは同じファイルの書き直しで削除ではない）。不要になった世代・ステージングは `garbage` / `discarded_at` に載せて GC に任せる。
- マニフェストの読み書きは必ず `UploadLocks` の鍵の中で行う（Task 2 の `with_manifest`）。
- 名前: ステージング `.spindle-upload-<16hex>`、マニフェスト `upload.json`、公開先の最上位 `upload/`、アルバム名なし `upload/_untitled/<origin 名>/`、サイドカーの記録 `upload`。
- 受ける音声の拡張子（アップロード専用の許可リスト）: `flac` `wav` `m4a` `aif` `aiff` `mp3` `opus`。zip は `zip`。それ以外は「取り込まない」。
- 同梱ファイルは `is_companion_name`（Task 1 で PDF と画像を足したもの）。
- チャンクは 32 MiB（web）、サーバの 1 リクエスト上限 40 MiB（`upload::CHUNK_LIMIT`）。
- `[upload]` の既定: `max_file_bytes = 8 GiB`、`max_upload_bytes = 32 GiB`、`max_zip_entries = 10000`、`stale_days = 30`。
- ユーザ向け文言（状態）: `同じ音声がライブラリにある` / `Inbox に同じ件がある` / `ライブラリの『<album>』（N 曲）に追加` / `Inbox で名前を入れる` / `新規`。
- ナビの並び: `ライブラリ / アルバム / CD / YouTube / アップロード / Inbox / 端末`。スマホ版には出さない。

## Review Focus

1. 公開の途中（組み立て中・宛先を書いた後・rename の直後・マニフェスト更新前）で落ちて再実行 → 件を二重に公開せず、取りこぼさない。公開した件が先に Inbox の配置で消えていても完了と判定する（Task 8）。
2. 同時 2 本の PUT・同じ origin への二重 PUT・PUT と PATCH / 展開 / GC の競合 → マニフェストの更新を失わず、予算を超えない（Task 4・5・11）。
3. ジョブを投入する前に落ちた / DB を消した → 照合が展開・公開のジョブを投入し直す（Task 9）。
4. 危ない zip（`../`・symlink・同名衝突・壊れた中央ディレクトリ・暗号化・展開サイズ超過・複数 zip の累積）→ 拒否・失敗を記録し、Inbox の外にも他の origin にも何も書かない（Task 5）。
5. 曲 0 曲の件・展開中の DELETE・公開要求後の PATCH → API が断り、Inbox に現れない件を作らない（Task 7・10）。

- 規則（設計 §5.3）: 鍵の中で始める前の検査（`discarded_at` 無し、origin が完了した zip で removed でない、`generation == 0`、`error` があれば `retry && retryable` のときだけ `error` を消して進む）、`unpacking` が残っていれば（再起動で止まった世代）その世代を garbage に残したまま `unpacking = None` にし、世代 `G = next_generation` の予約（`next_generation += 1`、`unpacking = Some(G)`、`garbage` に `x/<id>/g<G>`（bytes 0）を先に載せる = 失敗・停止しても GC が拾う）だけを行い、展開そのものは鍵の外。**書く前に**鍵の中で次のブロック 8 MiB ぶんを `garbage` の `g<G>` の bytes に足し（`used_bytes` が上限を超えるならやり直せない失敗）、それから鍵の外で書く。終わったら鍵の中で bytes を実際に書いた量に直す。取り消しと予算はコピーのバッファごとに見る。UTF-8 として読めないエントリ名は `Rejected`。エントリごとに `validate_client_path`、symlink（unix mode の S_IFLNK）・特殊ファイル・`canonical_key` 衝突・ファイルとディレクトリの衝突・親がファイルは `Rejected` に記録して続行。`__MACOSX/` は飛ばす。暗号化・対応外の圧縮方式・中央ディレクトリが読めない・エントリ数超過・予算超過は zip 全体のやり直せない失敗、展開中の空き不足（64 MiB ごとに `free_bytes`）・I/O エラー・取り消しはやり直せる失敗（`ZipState.error`、`unpacking = None`、世代は garbage に残る）。成功したら鍵の中で `generation = G`、`written_bytes` = 実際の量、`rejected` を書き、`unpacking = None`、`garbage` から `g<G>` を外し、旧世代（あれば）をその `written_bytes` で足す。
